## 2. Исходное ТЗ и границы frontend/backend

### UC-1. Блокировка

- Users list: 8 последних созданных пользователей; меню **Ban in the system**.
- Подтверждение: `Are you sure you want to ban __Username__?`.
- Причины: **Bad behavior**, **Advertising placement**, **Another reason**. Для Another reason появляется ввод текста.
- После Yes пользователь блокируется и теряет доступ к системе; все его комментарии и реакции — лайки/дизлайки — скрываются и не учитываются. **Скрытие не означает физическое удаление**.
- No/закрытие формы не вызывают блокировку. Ручная проверка — только новый disposable user через Swagger; существующие аккаунты студентов не блокировать.

### UC-2. Разблокировка

- Users list: 8 последних записей. Фильтр: **Not selected — все; Blocked — заблокированные; Not blocked — незаблокированные**.
- Меню **Un-ban**, подтверждение `Are you sure you want to un-ban __Username__?`.
- Yes разблокирует; No/крестик ничего не меняют.
- **Принято ранее:** unblock не восстанавливает отозванные сессии, нужен новый login.

### UC-3. Общий список платежей

- Отдельный **Payments list** всех пользователей платформы, не `superadminUser.payments`.
- Колонки: фото пользователя, username, дата, сумма, подписка, метод оплаты.
- По умолчанию 6 последних записей; на странице 6 записей.
- Поиск по username; сортировки по username, Date added, Amount, Payment Method. Направления и точный смысл части колонок в ТЗ не заданы.

Frontend: меню/диалоги, выбор причины/текста, Yes/No, визуальные таблицы. Backend: контракт, validation, сохранение/чтение, фактические access/visibility ограничения. Backend-тесты не подтверждают диалоги и не должны вызывать mutation при No/закрытии. UI не получает навязанных дополнительных колонок.

### Scope / Out of scope

**Входит:** совместимое расширение существующей moderation причиной и atomic audit, фильтр существующего Users list, узкий Payment-side profile read model/sync и полноценный общий административный Payments list с принятыми поиском/сортировками. Переиспользовать auth/context/guards/CSRF, audit/row lock/session revoke/outbox patterns и существующий Payment gRPC channel. Текущая готовность оценивается по этому сокращённому объёму, без claims полного visibility UC-1.

**Не входит:** frontend, Jira, новый сервис/брокер/IAM/event-платформа, comments/likes/dislikes source, любые подготовительные задачи его создания и сама visibility/её подсчёты, реальные платежи, Stripe/PayPal lifecycle, cancellation/refund/auto-renew, hard delete/restore, очистка публичных данных, реальный social graph и public read/edit API причины. Admin credentials/fallbacks, FOLLOW-ZERO-1, soft delete и прочие независимые решения не переоткрывать. Чужая БД напрямую не читается; user GetPaymentHistory и REST history сохраняются.

## 4. Принятые решения по moderation и совместимости

**Согласовано пользователем 25.10.2026 (R1/R2):**

- Старый block без причины остаётся допустимым; новый frontend передаёт причину. Старым блокировкам причина не придумывается. Нет срока автоматического отключения legacy вызова и нет breaking required input.
- Повтор BLOCK → ALREADY_BLOCKED, текущая причина не меняется, новых revoke/outbox для этого no-op нет; один audit результата сохраняется. Отдельного API редактирования причины не будет.
- UNBLOCK очищает текущую причину, история остаётся в audit. Сессии не восстанавливаются, нужен новый login; приоритет DELETED и прежние outcomes сохраняются.
- ANOTHER_REASON: обязательный текст после trim, 1–500 символов. Стандартные причины: непустой после trim свободный текст отклоняется; пустой нормализуется в null. Если reason передан, validation выполняется до изменения данных.
- Причина, isBanned, session revoke, audit и существующий revoke outbox используют одну Gateway tx и прежний User row lock. Сбой audit/outbox откатывает переход; tx не удерживается во время publish. Actor берётся из principal.
- **Чтение причины в admin list/detail в текущий объём не входит.** Хранить текущую причину и историю достаточно; не добавлять banReason в response/SDL как «удобную» незаданную колонку.

**Техническая форма на review, без альтернативной бизнес-семантики:** оставить `SuperadminUserIdInput!` неизменным и добавить optional аргумент `reason: SuperadminBanReasonInput` только к существующей block mutation. Так старые documents/variables продолжают валидироваться, delete/unblock не получают лишних полей. Не создавать вторую mutation/механизм блокировки. Omission/null reason у legacy первого block → null code/text, не выдуманный BAD_BEHAVIOR/ANOTHER_REASON; новая FE-форма передаёт reason.

В модели — nullable `User.banReasonCode/banReasonText` и nullable reason snapshot существующего AdminUserActionAudit. Коды BAD_BEHAVIOR / ADVERTISING_PLACEMENT / ANOTHER_REASON соответствуют трём причинам ТЗ. Это проект хранения для S2, не уже существующие поля. Текст — plain text, не HTML; frontend экранирует вывод. Техническая детализация audit: BLOCK/ALREADY_BLOCKED фиксирует сохранённую причину результата, UNBLOCK — причину до очистки; прежние audit rows не переписываются, проигнорированный новый текст не выдаётся за текущую причину. Legacy/missing/deleted → допустимый null. Schema/typed writer должны сохранять прежние гарантии и не логировать свободный текст.

При расширении entity/mapper/save paths проверить, что обычное сохранение устаревшей User entity не очищает причину. Пользовательские DTO её не принимают. Internal locked read может читать причину для транзакции/audit — это не новый публичный read API.

**Комментарии/реакции — решение пользователя R3, отложено вне текущей итерации:** пригодного источника в проверенном репозитории нет (границы доказательства E9 сохранены). Новую comments/likes/dislikes подсистему и подготовительные задачи её создания не включать. Скрытие и исключение из counts отложены до настоящего источника, отсутствие source не блокирует filter/reason/Payments. Не создавать фиктивные endpoints ради отметки о заглушке, найденные существующие заглушки сохранять.

Будущая политика согласована: после unblock действия снова видимы/учитываются, если нет другого основания скрывать. Сейчас она **не реализуется и не проверяется**. Виды targets и конкретные read/count predicates определяются при будущем появлении source; не создавать реакции на новые виды объектов по аналогии. E8 revoke v1 не объявляется готовой visibility-синхронизацией. Готовность сокращённого объёма отделяется от **невыполненного исходного visibility-требования UC-1**.

## 5. Общий Payments list: принятая граница сервисов и sync

### Принятая архитектура R8

**Согласовано пользователем 25.10.2026:** узкий read model в Payment DB, не реплика платежей в Gateway. Gateway остаётся owner User/Profile; Payment хранит только userId, username, признак удаления и технические state/version признаки. Все filters/order/count выполняются на Payment стороне **до** pagination. Username ответа берётся из того же snapshot проекции. Фото Gateway обогащает одним локальным ограниченным SELECT для ≤6 distinct user IDs страницы. Нет прямого доступа к чужой БД, unbounded IDs, полной загрузки записей в память, нового сервиса/брокера или универсальной event platform.

GetPaymentHistory(user_id,...) остаётся без изменения. Новый admin-oriented read RPC возвращает userId строки и общую страницу, использует существующий PaymentGrpcClient/channel/error mapping. Обогащение уже полученной страницы не может заменить глобальный username search/sort. Вариант репликации платёжных строк в Gateway **отклонён для этой итерации**, это не параллельное готовое решение.

**Eventual consistency принята:** две БД не совпадают мгновенно; при сбое копия может временно устареть, после восстановления обязана догнать источник. Нет числового SLA задержки без измерений и нет общей cross-service транзакции. Внутри Payment DB count/items и username для сортировки/вывода читаются одним SQL snapshot либо explicit Repeatable Read tx. Обычная пара запросов в READ COMMITTED это не гарантирует (E10).

Все исходные rows получают version 0 и попадут в export без выдуманных событий. Новый User — версия 1. Каждое **фактическое** изменение profileExists/username/isDeleted увеличивает версию ровно на 1 в SQL под User lock, не из старой entity/часов. User create без Profile даёт snapshot v1; последующий Profile create — v2, даже если оба в одной registration tx: две outbox rows коммитятся атомарно, финальный version=2. Не нужны отложенные commit hooks/coalescing. Изменение имени на то же значение, avatar-only, BLOCK/UNBLOCK и повтор DELETE версию не увеличивают. Source overflow BIGINT — безопасная ошибка/rollback, не wraparound.

Событие `PaymentUserProfileChangedV1`, JSON envelope **ровно**:

```json
{
  "eventType": "payment.user-profile.changed.v1",
  "schemaVersion": 1,
  "eventId": "10000000-0000-4000-8000-000000000001",
  "occurredAt": "2026-10-25T12:00:00.000Z",
  "userId": "20000000-0000-4000-8000-000000000001",
  "sourceVersion": "2",
  "username": "synthetic_username",
  "profileExists": true,
  "isDeleted": false
}
```

`sourceVersion` — каноническая decimal-string `0|[1-9][0-9]*` в диапазоне PostgreSQL signed BIGINT (0..9223372036854775807). В JS — BigInt для сравнения/SQL, **никогда Number/parseInt**; JSON/proto version всегда `string`, не uint64/int64, поэтому существующий `loader.longs=Number` и generated timestamp conventions менять не требуется. Версия схемы события (`schemaVersion=1`) и версия состояния пользователя различаются. eventId=outbox.id стабилен при retry, AMQP messageId=eventId. occurredAt — диагностическое время, не критерий порядка. Не включать email, avatar, credentials, session или токены.

Snapshot инварианты: без Profile → profileExists=false/username=null; live Profile → profileExists=true/username содержит исходное имя без нормализации алфавита; deleted → isDeleted=true/username=null независимо от сохранённого Profile, profileExists отражает его наличие. Блокировка не скрывает имя/платежи. JSON null соответствует отсутствующему proto optional username; пустая строка не используется как null. Существующая `Profile.username` NOT NULL подтверждена [Gateway schema](apps/main-gateway-service/src/core/prisma/schema.prisma). eventId валидируется как UUID, userId — непустой source TEXT ID (обычные UserEntity создают UUID, schema User.id остаётся TEXT, в том числе для legacy fixtures); одинаковый ID переносится без преобразования. Технические booleans/version/shape валидируются на обоих концах; неизвестная схема/повреждённая пара не применяются.

#### P0.3. Доставка, применение, retry и poison messages

- Existing durable topic exchange `common_exchange`; routing key `payment.user-profile.changed.v1`; одна durable queue `payment.superadmin.user-profile.v1`, exclusive=false/autoDelete=false. Несколько Payment instances — competing consumers, не WS fan-out. Только для этой очереди: retry queue `payment.superadmin.user-profile.v1.retry`, routing key `payment.user-profile.retry.v1`, TTL 60000 ms, DLX обратно на основной key; DLQ `payment.superadmin.user-profile.v1.dlq` с key `payment.user-profile.dead.v1`. Все binding/queues создаются **до** producer rollout.
- Новый узкий Gateway relay повторяет claim `FOR UPDATE SKIP LOCKED`/lease образец [UserAccessRevokeRelay.relay](apps/main-gateway-service/src/modules/users/infrastructure/outbox/user-access-revoke-relay.ts): одна row, lease 30 s, publish bound 5 s, retry 2..60 s; mark published/retry только при совпадающем leaseId. Source transaction закрыта до сети. AMQP persistent=true/mandatory=true, confirms + корреляция `basic.return` по messageId; ack брокера для unroutable сообщения **не** означает успех.
- Для mandatory return/confirm взять узкий publisher-pattern [PaymentOutboxPublisher.confirmPublish](apps/micro-payment-service/src/modules/payment/infrastructure/messaging/payment-outbox.publisher.ts) на уже установленном amqplib; один scoped confirm connection/channel Gateway-процесса к прежнему GatewayConfig.rabbitmqUrl, без новых dependencies/брокера. Не переиспользовать сам Payment publisher с его allow-list business events. `AmqpConnection.publish` revoke relay не считать автоматически доказательством correct basic.return handling нового потока: P1 проверяет unroutable publish реальным RabbitMQ. [Avatar relay](apps/main-gateway-service/src/modules/users/infrastructure/outbox/avatar-outbox-relay.cron.ts) и revoke payload/table остаются независимыми.
- Payment scoped consumer использует установленный amqplib/`PaymentConfig.rabbitUrl` (RABBITMQ_URL), manual ack; существующий PaymentModule не содержит готового профильного consumer. Нормальное сообщение: DB tx upsert/commit → ack. Один SQL conditional apply: absent → insert, incomingVersion > stored → update, меньше → no-op; равная версия с тем же snapshot → no-op. Равная версия с другим содержимым → protocol conflict в DLQ, не silent overwrite. Дубликаты eventId не требуют отдельной inbox таблицы: guard состояния достаточен. Удалённая target row не становится live даже при более новой ошибочной команде — protocol conflict/DLQ; restore вне scope.
- Transient DB failure: confirmed persistent republish в retry queue (header `x-payment-profile-retry-count` +1), затем ack original; повторять с 60 s задержкой без hot requeue, число повторов наблюдаемо. Malformed/unknown schema/tombstone conflict: confirmed publish в DLQ с безопасным reason code, затем ack original, без бесконечного invalid-message retry. DLQ доступна только операторам, payload не попадает в logs. Паттерн delayed retry/DLQ подтверждён [PaymentRabbitConsumer.retryOrDeadLetter/deadLetterTerminal](apps/main-gateway-service/src/modules/users/infrastructure/payment.rabbit.consumer.ts); это переиспользование алгоритма, не его payment-entitlement очереди.
- Если confirm retry/DLQ не получен, original **не ack**; consumer прекращает получение/закрывает канал, reconnect с backoff 30..60 s. Это избегает немедленного nack/requeue цикла; original может быть доставлен снова после восстановления. Crash после DB commit или republish, но до ack безопасен: возможен повтор, версия/полный snapshot защищены. Потеря commit при DB failure не даёт ack.

Не переиспользовать `GetUserById` (поля email, обычные правила чтения), не публиковать REST/GraphQL export.

| Message                             | Поля / правила                                                                                                                                                                                                                 |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ExportPaymentUserProfilesRequest`  | `optional string after_user_id`, `optional string upper_user_id`, `int32 limit`. Limit 1..500, worker всегда передаёт 500; invalid → INVALID_ARGUMENT. Первый запрос без обоих cursor/bound; after задан только вместе с upper |
| `PaymentUserProfileSnapshot`        | `string user_id`, `string source_version`, `optional string username`, `bool profile_exists`, `bool is_deleted`; те же инварианты/version, что JSON event без envelope                                                         |
| `ExportPaymentUserProfilesResponse` | `int32 protocol_version=1`; `optional string upper_user_id`; `bool source_empty`; `repeated PaymentUserProfileSnapshot items` (≤500); `optional string next_after_user_id`; `bool complete`                                    |

Первая страница **одним SQL statement/snapshot** вычисляет MAX(User.id) и читает User LEFT JOIN Profile до этого upper bound включительно. Порядок/операторы `> after`, `<= upper`, MAX/ORDER используют **одну фактическую collation User.id** существующего PK; не сравнивать cursor на клиенте как UUID-number и не менять collation/алфавит. Cursor — исходный opaque source ID, после последнего возвращённого User; имена/createdAt курсором не являются. Для has-more допускается fetch limit+1 строк (≤501 внутри DB), клиенту ≤500. Последующие страницы читают по тому же сохранённому bound; after < upper, равенство допускается как пустая завершённая страница. upper без after допускается для повтора первой страницы с уже сохранённым bound. Заданный пустой cursor/bound, after без upper или after > upper по source collation → INVALID_ARGUMENT; ID передаётся как исходный TEXT без UUID-number преобразования. Никакой SQL-конкатенации.

Пустой источник: верхняя граница отсутствует, source_empty=true/items=[]/next absent/complete=true. Непустой источник: source_empty=false, upper присутствует и повторяется в каждом response; next=последний item либо исходный after для пустой завершённой страницы. Не придумывать UUID sentinel. Полный empty response позволяет закончить bootstrap **и** запланировать следующий проход. Ошибка/timeout экспорта не являются empty source. На завершённом пустом проходе источник, выросший позднее, догоняется live events/следующей сверкой.

User/Profile/version выбираются одним statement, включая deleted rows; нет отдельного SELECT Profile на строку. Нет long-lived DB snapshot на весь проход. Initial bound/page/cursor сохраняются только вместе с apply response в Payment tx; crash до сохранения первой страницы допускает повтор с новым bound, при тех же version guards. Если bound уже сохранён — после restart он не меняется до complete. Protocol version должен быть 1, boundary/порядок/размер response валидируются; несовместимый response не продвигает cursor.

#### P0.5. Ownership, readiness и гонки bootstrap/live

- Один export worker владеет singleton `AdminUserProjectionSync`: claim/update под row lock при leaseUntil≤DB now, новый random leaseOwner + **увеличенный leaseGeneration**. Lease=30 s, export timeout=5 s; перед каждым RPC обновить lease только если owner/generation совпадают и lease ещё действителен. Сеть вне tx. Несколько Payment instances не запускают независимые full scans.
- После ответа tx **сначала** блокирует sync row и проверяет owner/generation/неистёкший lease по текущему DB clock_timestamp(), затем apply всех rows и cursor/bound/phase атомарно. Финальный conditional sync UPDATE повторно проверяет lease по clock_timestamp(); expiry во время apply откатывает всю пачку. Не использовать застывший transaction_timestamp/now() как проверку действующего lease после ожидания lock. Несовпадение → rollback всей пачки, включая projection changes. Старый worker после takeover не может обновить ни данные, ни cursor/ready; generation не сбрасывается между passes. Live consumer lease worker не требует и использует тот же version-guarded apply.
- `lastBatchAt` и next eligibility хранятся в singleton: перед RPC fenced UPDATE под lock проверяет throttle и фиксирует время начала попытки; между началами экспортов не менее 1 s даже при смене worker, batch cap 500. Это техническая отметка, не advancement cursor: cursor изменяется только с apply. При timeout backoff export 30..60 s без продвижения cursor. DB/service restart продолжает pass с последнего committed cursor; новый проход только после завершения предыдущего либо явного операторского cancel/restart через внутреннюю DB-процедуру, не UI endpoint.
- READY впервые: durable consumer/queue зарегистрированы и consumer подключён, operator подтвердил rollout **всех** source writers (sourceWritersConfirmedAt + фактическая deployment revision в singleton), совместимый export завершил baseline целиком, last batch/complete/phase=READY зафиксированы одной fenced tx. Ответ одного Gateway/пустая queue не подтверждают обновление всех pod. До подтверждения writers bootstrap не начинается; auto-ready по одному новому pod запрещён.
- Initial phase NOT_READY → LOADING → READY; фоновая сверка меняет mode, но после первого READY не сбрасывает phase. NOT_READY/LOADING, feature disabled или недоступная sync table → admin read unavailable, не нули. READY **не** является нулевым lag: после baseline допустим ещё не применённый live/outbox хвост; временный Rabbit/export outage не стирает READY и сам по себе не превращает уже полную базовую копию в ошибку чтения. DB failure остаётся ошибкой; накопление lag/outbox/retry/DLQ диагностируется, без ложного SLA.

| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Новый случайный UUID появился позади cursor либо выше upper | Все Gateway уже выполняют atomic create/version/outbox. Export может не увидеть row, но её durable live snapshot обязателен; до catch-up возможен согласованный live lag. Один baseline без live stream этого не гарантирует |

| Сначала пришёл live vN, затем старый batch vN-1             | Apply не заменяет более новую target версию. Tombstone не отменяется                                                                                                                                                         |
| Batch commit без cursor либо cursor без apply               | Запрещено: один fenced Payment tx. Crash до commit → повтор batch, после commit → resume next                                                                                                                                |

#### P0.6. Сверка и операторское восстановление

**Принятые стартовые параметры:** один полный bounded pass раз в 24 h, ≤500/пачку, ≤1 пачки/с. `nextRunAt=lastCompletedAt+24 h`; при просрочке после рестарта claim один pass, не по проходу за каждый пропущенный день. Существующий незаконченный pass сначала resume. Не сканировать на UI-запрос, не опрашивать всю БД каждую секунду. Системный scheduler проверяет лишь singleton readiness/nextRunAt, а не source tables.

Неоднозначную автоматику «после длительного восстановления» **исключить**: без отдельного threshold/измерений нельзя угадать длительность. Остаются durable retry, ежедневный проход и воспроизводимая внутренняя operator procedure: проверить broker/export/DB и единый source revision → исправить DLQ-причину/допустимо replay → fenced коротким UPDATE sync row установить nextRunAt=DB now при mode=IDLE. Если pass уже идёт — продолжить его, не сбрасывать cursor. Для принудительного restart оператор сначала атомарно инвалидирует lease (generation+1, owner=null), затем сбрасывает cursor/bound/pass в новой generation; старый worker не пишет. Это runbook/DB-operation владельца Payment, **без публичного recovery endpoint**, новой job платформы или обязательного скрипта текущего P0.

Сверка применяет missing/более новую source version тем же upsert. Для equal-version/different-content trusted export отдельно делает bounded conditional repair под target row lock/CAS только пока storedVersion всё ещё равна incoming; tombstone→live repair запрещён. Отмечает безопасный protocol-conflict counter; live event с равной версией не получает это право. Если export.version < target.version — target не трогать, диагностировать SOURCE_BEHIND, не «чинить» downgrade. Reconciliation/version guards не заменяют исправление source writers и не обещают поддержку произвольных ручных SQL updates.

Порядок rollout:

1. Применить Gateway additive migration version/outbox и Payment additive read-model/sync migration штатно; старый User/Payment history совместим. 2. Развернуть **все** Gateway source writers + отдельный relay + export protocol 1. Ранние publishers допустимы только с уже durable binding. Старые writers не повышают revision и могут потерять rename без события: поэтому rollout gate обязателен. Нельзя объявлять «полный bootstrap» в mixed-version deployment; rolling upgrade/restart не отменяют outbox/consumer обязательства.
3. После проверки revisions всех Gateway operator фиксирует sourceWritersConfirmedAt/revision в sync singleton; выполнить/resume initial export. Версии 0 экспортируют существующих users; live stream уже работает и защищает boundary.
4. После fenced complete/READY P2 может обслуживать новое общее чтение (до этого честная unavailable). Отдельный readiness для нового admin read, не глобальный stop старого GetPaymentHistory/Checkout/Stripe. Новый Gateway→Payment admin method при старом Payment даёт безопасный upstream unavailable, без retries/empty fallback. Downgrade Gateway на старые source writers требует снова закрыть readiness общего чтения оператором и нового bootstrap после исправления rollout; не оставлять ложную гарантию.

Проверки env/network, фактическое применение миграций и operator rollout marker остаются **deployment conditions**, не выполненными действиями P0. Ни manifests, ни env сейчас не менялись.

### Enrichment и различение отсутствия/ошибки

Gateway одним локальным запросом читает User/Profile для ID страницы, **включая deletedAt**. Не использовать обычный repository, скрывающий deleted, если это не позволяет отличить состояние.

- User жив, Profile есть: username остаётся из Payment snapshot, avatar из текущего Gateway Profile; не подменять username свежим значением после сортировки.
- User жив, Profile отсутствует: avatar=null; source profileExists=false/username=null является нормальным отсутствием Profile. Если профиль создан после snapshot, временно старый username допустим до sync; полнота не выдумывается.
- User уже deleted либо отсутствует в Gateway: username и avatar **обязательно null**, даже если проекция ещё содержит старое имя. Платёжная строка сохраняется. Это защитное исключение из snapshot username для устаревшего профиля, не пересортировка/удаление строк после pagination.
- Missing projection row **не доказывает**, что User отсутствует в Gateway. Для выбранной страницы batch различает неизвестного source User и живого User с отсутствующей копией: второе — sync gap/unavailable, а не выдуманный null Profile. До ready gap вообще не выдаётся как нормальные данные. Ошибка БД/RPC не приравнивается к unknown user/profileless; запрос завершается безопасной ошибкой.
- После sync deleted/missing username не матчится непустым search. **При гонке** search/count могли выбрать строку по ещё старому username, а enrichment уже обнулит профиль. Не менять затем count/страницу, не загружать все записи для компенсации: состав/totalCount отражают snapshot отстающей проекции, после catch-up результат поиска изменится. Это явное ограничение согласованной eventual consistency, не обещание общего snapshot двух сервисов.

### Внутренняя граница доступа

Переиспользовать существующий внутренний gRPC channel и Gateway admin guard. PaymentGrpcController E12 не проверяет admin principal/caller identity; [Payment Service](apps/micro-payment-service/service.yaml) описывает внутренний Service с gRPC port, без внешнего типа. Это подтверждает способ подключения, **не** наличие authenticated caller/mTLS или проверенной NetworkPolicy. Новый admin read и Gateway export не публиковать через внешний HTTP/GraphQL user API, не передавать admin cookie/token в MS. Для окружения Operations проверяет отсутствие публичного ingress/port exposure и существующие сетевые ограничения; если их фактически нет, это deployment/security условие, а не повод изобретать IAM или объявлять RPC защищённым аутентификацией. Архитектура R8 принята, новые IAM-вопросы не блокируют независимый Users filter.

## 6. API: фильтр опубликован, остальные дополнения ещё кандидат

Продуктовые R1/R2/R4–R8 решены пользователем; технические имена/формы ниже проверяются при review этой версии плана. Не менять target/runtime SDL до реализованных resolvers/tests. Владельцы common SDL/guards/pagination/errors остаются Gateway integrator; Payment proto/generated — Payment+Gateway contract owner, один integration PR. S1 опубликовал additive banFilter в версии 1.3.0. S3 добавляет optional reason только существующему block в composition/target/runtime export **1.4.0**, без новых operations/response fields и breaking required reason. Общий Payments в runtime ещё не добавлен.

**Users:** ALL → без нового predicate; BLOCKED → isBanned=true; NOT_BLOCKED → false. Все варианты сохраняют deletedAt IS NULL, независимый isEmailConfirmed, search/sort, joined snapshot count/items. UI Not selected соответствует ALL. Добавить enum/default/проверку, тип фильтра и SQL clause — не второй Users list. Старые запросы без banFilter сохраняют поведение. Defaults/bounds 1/8, page≤10000/pageSize≤50 и normalized search≤100 сохраняются (E5 и [PaginationInput](libs/common/src/graphql/pagination-input.ts)).

**Причина:** reason отсутствует/null → legacy вызов без причины допустим. Если объект передан, code обязателен и валидируется, ANOTHER_REASON требует trimmed text 1..500, стандартные причины отклоняют непустой text. Неверные code/text → BAD_USER_INPUT до tx; UUID/outcomes и actor из principal прежние. ALREADY_BLOCKED не редактирует причину, USER_DELETED/NOT_FOUND её не создают. **Не добавлять reason/banReason в admin list/detail output**, новый read API или edit-reason mutation. Внутреннее хранение/чтение для use case/audit — S2/S3.

**Payments:** fixed pageSize=6, новый input не открывает pageSize клиенту и не меняет общий PageInput default=8. Переиспользовать page validation 1..10000 и PageInfo; internal RPC получает page*size=6. Search как каталог: trim, empty→no filter, literal case-insensitive substring, normalized max100; null username не матчится. SQL параметры; %, *, backslash и кавычки — текст, без wildcard синтаксиса.

`SuperadminPaymentsPage`: non-null items/totalCount/pageInfo, nullable root query для UPSTREAM_UNAVAILABLE без потери других root data. Строка содержит transactionId/userId, nullable username/avatarUrl, createdAt DateTime, amountMinor/currency, productName/billingInterval/billingIntervalCount, provider/status. Новые card details, «исторический snapshot продукта», FX или поля ради неопределённой функции не добавлять. Reuse enums/DateTime/safe Int bounds. Смысл полей согласован в разделе 5; технический SDL-кандидат не объявляется уже опубликованным API.

Пустая выборка: items=[], totalCount=0, pageInfo={page, pageSize:6, pagesCount:0, hasNextPage:false}. Допустимая page за диапазоном: items=[], count/pagesCount всей отфильтрованной выборки, hasNextPage=false. Count/order до LIMIT/OFFSET в Payment DB; между запросами страниц стабильность при изменениях не обещается. Username null-last, ID tie в направлении основного ключа, Amount — raw amountMinor без FX, метод — provider code, не локализованный label. Все статусы как user history.

После source catch-up deleted/missing users не входят в непустой username search. При concurrent enrichment suppression возможен описанный в разделе 5 временный stale search/count с null профилем; не обещать общий snapshot и не переписывать count по одной странице.

Timeout нового RPC — конечный существующий лимит, без automatic retry. Outage/not-ready/timeout → null + UPSTREAM_UNAVAILABLE с корректным path/alias; auth → UNAUTHENTICATED/FORBIDDEN, input → BAD_USER_INPUT, неожиданные ошибки → безопасный INTERNAL_SERVER_ERROR. Ошибки не превращаются в items=[], а unknown user/profileless не смешиваются с storage failure. Старое `superadminUser.payments` и его null boundary не меняются.

Все статусы включены, transaction row не исключается по состоянию User. Search — `strpos(lower(effective_username), lower($search)) > 0`: literal %, \_, *, backslash/quotes, без LIKE/wildcard-синтаксиса; normalized max100 как каталог. Count от **filtered**, selected ORDER BY/LIMIT 6/OFFSET (page-1)*6. Seed/LEFT JOIN sentinel сохраняет count для пустой/out-of-range страницы. Нет count-over-window-only, теряющего totalCount на пустой странице. Missing sync row/phase!=READY возвращает отдельный not-ready сигнал → UNAVAILABLE, не count=0.

ORDER BY — закрытая SQL-map enum → static fragment: username ASC/DESC **NULLS LAST**, created_at ASC/DESC, amount_minor numeric ASC/DESC, provider code ASC/DESC; затем payment transaction `id` в том же направлении (UUID native order). Не sort в памяти, не передавать username-list или user IDs для глобального поиска. Username search case-insensitive, sort использует фактическую Payment DB collation без lower/неоговорённой нормализации алфавита. Collation окружения записать в P1/P2 DB evidence; совпадение порядка разных installations заранее не обещать. Индексы/EXPLAIN оценить на этой модели до добавления, без универсального индексирования/новой search-системы.

**Ошибки/timeout:** invalid RPC request → gRPC INVALID_ARGUMENT(3); projection disabled/NOT_READY/LOADING/storage temporarily unavailable → UNAVAILABLE(14); server unexpected/повреждённые данные → INTERNAL(13), с безопасными фиксированными сообщениями. Gateway применяет существующие GrpcErrorMapper/GraphQL formatter и feature boundary: upstream outage/not-ready/timeout/malformed response → root `superadminPayments: null` + `UPSTREAM_UNAVAILABLE` с фактическим path/alias; auth/CSRF не переклассифицируются, invalid frontend input → BAD_USER_INPUT до RPC. Unexpected Gateway programming error → прежний INTERNAL_SERVER_ERROR. Не возвращать fake empty list при ошибке.

Новый read использует **существующий** `SuperadminPaymentsConfig.timeoutMs` / `SUPERADMIN_PAYMENTS_TIMEOUT_MS` (fallback 3000, допустимо 1..30000), без новых env/retry. Как [PaymentGrpcClient.getPaymentHistoryWithTimeout](apps/main-gateway-service/src/modules/payments/infrastructure/payment-grpc.client.ts), RxJS timeout → unsubscribe/cancel unary call; это client-side bound, не автоматически propagated gRPC deadline. P2 проверит cancellation реальным transport. Export worker отдельно использует технический bound 5000 ms/вызов, с описанным worker retry, не UI retries.

## 9. Правила реализации и обновления прогресса

**Правило минимального scope пользователя:** упоминание неопределённой функции/отсутствующий источник не разрешает строить новую domain подсистему. Существующую заглушку сохранять; при необходимости только предложить минимальное явно документированное ограничение/заглушку, без новых API/моделей исключительно ради неё. Для comments/reactions сейчас новые endpoints/заглушки не создаются. Это **не** разрешение заменить реальные платежи, upstream errors или результаты поиска фиктивными нулями: согласованные reason/filter/global Payments реализуются полноценно. Отложенное visibility-требование явно не выполнено.

- Понятные domain names, небольшие функции с одной задачей, явные типы на границах, thin resolvers. Читаемые условия вместо вложенных тернарных выражений; не копировать существующий сложный conditional только из-за соседства.
- Следовать Agents.md/DDD: application errors — DomainException; domain/application без Prisma типов, инфраструктура через ports/действующий tx handle; common DTO/enums/contracts в соответствующих libs. Обычные пользовательские DTO не открывают moderation fields.
- SQL параметризованный/структурированный; order выбирается из закрытого enum, не конкатенация пользовательского SQL. Нет ненужных фабрик/универсальных frameworks/DataLoader без доказанного N+1.
- Комментарии объясняют причину/ограничения; errors идут через существующий safe mapping, без raw upstream/секретов. Не рефакторить независимый качественный код ради вкуса.
- Изолированные disposable fixtures/helpers, никаких student accounts/shared/production DB. Повторять общий regression только в конце или при затронутой общей защите; каждый слой проверять минимальным поведением/риском, не количеством tests.
- Готовые наборы для расширения, не новые платформы: [users integration](apps/main-gateway-service/test/superadmin/superadmin-users.integration-spec.ts), [moderation/access integration](apps/main-gateway-service/test/superadmin/user-access-enforcement.integration-spec.ts), [Payment HTTP/gRPC integration](apps/main-gateway-service/test/superadmin/superadmin-payments.integration-spec.ts); helpers [Gateway DB](apps/main-gateway-service/test/superadmin/isolated-admin-database.ts), [Payment DB](apps/main-gateway-service/test/superadmin/isolated-payment-database.ts), [RabbitMQ](apps/main-gateway-service/test/superadmin/isolated-rabbit.ts). В этом discovery они не запускались; реальные integration и test doubles отмечать отдельно в следующих проходах.
- После **реальной реализации и проверки** агент ставит `[x]`, пишет краткое доказательство/команду/результат и следующий незавершённый шаг.
