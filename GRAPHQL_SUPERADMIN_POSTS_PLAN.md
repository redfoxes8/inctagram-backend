## 1. Исходное ТЗ и границы

UC-1 — просмотр всех постов:

1. Суперадмин открывает Posts list.
2. Поиск по username; строки содержат фотографию поста, описание, дату публикации.
3. Infinite scroll.
4. Новый пост из публичной части появляется без обновления страницы.
5. Обязателен Apollo GraphQL Subscription. Polling и существующий Socket.IO отдельно это требование не закрывают.

Альтернативный сценарий: инициировать блокировку автора из поста → frontend показывает существующий диалог выбора причины → существующий block с reason. Отмена/закрытие не отправляют mutation. Меню, диалог, отображение, Apollo cache и прокрутка принадлежат frontend.

Backend: реальные посты, cursor query, поиск, защищённая GraphQL subscription, надёжное событие публикации и fan-out. Существующий публичный publish-path — источник, а не повод переписать public Posts CRUD.

Вне scope: комментарии/реакции/счётчики и их модерация, новый public CRUD/редактор/upload, admin edit/delete поста, новые причины и механизм блокировки, новый сервис/брокер/event framework, replay-журнал/exactly-once, realtime edit/delete/rename, поисковый движок. Отсутствующие второстепенные функции остаются defer; реальные посты и subscriptions заглушкой не заменяются. Credentials/fallbacks, FOLLOW-ZERO-1, Payments и ранее согласованный soft delete не переоткрываются.

## 3. Предложенная минимальная архитектура

### 3.1 Принято: Post username-проекция и SQL pagination

Пользователь выбрал узкую проекцию в **Post DB**. Gateway остаётся владельцем User/Profile; Payment не источник пользователей. Поиск — SQL JOIN Post с локальной проекцией **до** cursor pagination. Страница заполняется до first при достаточном числе совпадений в состоянии проекции. Предыдущий bounded candidate scan отклонён: нет промежуточных пустых scan-pages и кнопки продолжения поиска. totalCount не добавляется.

Выбранные локальные имена: `PostAdminUserProfile` → `post_admin_user_profile`, `PostAdminUserProjectionSync` → `post_admin_user_projection_sync`, singleton `post-user-profile-v1`. Поля row: userId TEXT PK, sourceVersion BIGINT, username nullable TEXT, profileExists, isDeleted. Без email/avatar/credentials/sessions и полной копии User/Profile. profileExists отличает отсутствие Profile от tombstone. Blocked автор не исключает Post: isBanned не добавляется, новых moderation events нет. Post.ownerId UUID сравнивать через безопасное текстовое представление, не приводить произвольные source TEXT IDs к UUID.

Initial readiness: NOT_READY → LOADING → READY. Наличие таблицы/пустой очереди не означает READY. Sync disabled/NOT_READY/LOADING/storage failure → query root=null + UPSTREAM_UNAVAILABLE, не пустая лента. Phase и данные читать одним SQL statement/snapshot. RECONCILE не сбрасывает достигнутый READY; READY не означает lag=0. Subscription до initial READY завершается безопасной UPSTREAM_UNAVAILABLE, не выдаёт READY control event. Проверять projection readiness при старте и protected read/delivery; операторский сброс initial readiness завершает активные подписки для восстановления.

SQL: Post.deletedAt IS NULL, LEFT JOIN проекции (не INNER JOIN), literal case-insensitive username predicate, `(createdAt,id) < cursorTuple`, `ORDER BY createdAt DESC,id DESC`, `LIMIT first+1`. JOIN один-к-одному не размножает посты; фильтры до LIMIT. Tombstone/profileExists определяют nullable username; непустой search не включает null. Параметризовать search и tuple, экранировать `%`/`_`. Existing id-only cursor/skip не копировать: удаление граничного Post не ломает продолжение. endCursor — tuple последней **выданной** строки, пустой конец → null/hasNextPage=false. Размер: default4, 1..5 (расчёт budget в разделе5). Фото выбранных результатов — один File batch до50 IDs, order ASC,id ASC. Gateway не фильтрует/пересортировывает готовую страницу.

Поиск корректен относительно **Post projection**, а не мгновенного Gateway state: rename/delete доходят с задержкой. Username берётся из того же projection snapshot, по которому искали, без свежей подмены после pagination. Без search все неудалённые Post остаются, включая blocked/deleted/missing авторов и неизвестную projected row; CASE даёт null для отсутствующей row, profileExists=false или isDeleted=true. С непустым search участвует только имеющаяся live projection с username. Нет per-row Gateway lookup или повторной фильтрации query. До прихода tombstone/rename допустим stale username/search, а не обещание мгновенного совпадения БД.

Opaque cursor: base64url строгого JSON {v:1,createdAt:<canonical UTC ISO с миллисекундами>,postId:<UUID>,searchUsername:<normalized string|null>}; cap1024 bytes, только эти поля, date/UUID/version/filter валидируются → `BAD_USER_INPUT`. [Initial Post migration](apps/micro-post-service/prisma/migrations/20260509201552_init/migration.sql) подтверждает TIMESTAMP(3): миллисекунд достаточно, tuple сравнивается в DB, не через потерю точности/локальную timezone. Cursor не авторизация, новый secret не нужен. Search: trim, пустой→null, max100, буквальные `%`/`_`, case-insensitive substring. Смена search сбрасывает cursor.

#### 3.1.2 Post consumer, bootstrap, readiness и восстановление

Принято: **отдельная durable competing queue Post**, не Payment. Выбранные имена: common_exchange/topic, исходный key `payment.user-profile.changed.v1` без переименования; queue `post.superadmin.user-profile.v1`, retry queue `post.superadmin.user-profile.v1.retry` TTL60000, Post retry key `post.user-profile.retry.v1`, DLQ `post.superadmin.user-profile.v1.dlq`/key `post.user-profile.dead.v1`. Main Post queue bind к исходному key и Post retry key; retry возвращается только Post, не Payment. Retry публикуется адресно через стандартный default exchange (пустое имя) с routingKey=post.superadmin.user-profile.v1.retry. Эта queue не привязывается к common_exchange/Post retry key: её DLX возвращает в common_exchange именно с post.user-profile.retry.v1, связанный только с main Post queue. Так нет немедленной доставки retry в main, повторного зацикливания на retry queue или попадания в Payment. Оба сервиса получают исходное событие независимо, Post instances конкурируют внутри своей queue. Durable/non-exclusive/non-auto-delete; prefetch1 — стартовый параметр.

Live apply одной Post DB-транзакцией: absent→insert, newer→update, stale/identical→no-op, equal-content conflict/resurrection→DLQ, storage error→retry. Ack после commit или подтверждённой retry/DLQ публикации. Неподтверждённый publish → не ack, channel close/reconnect30..60s, без горячего requeue. Trusted equal-version repair — отдельный export-only метод с expected version.

Собственный singleton Post: phase NOT_READY/LOADING/READY, mode IDLE/BOOTSTRAP/RECONCILE, passId, upperUserId/cursor/sourceEmpty, lastBatchAt/lastCompletedAt/nextRunAt, sourceWritersConfirmedAt/sourceDeploymentRevision, leaseOwner/leaseUntil, leaseGeneration BIGINT. Миграция создаёт NOT_READY без marker. Подключённый **Post** consumer + подтверждение всех Gateway writers → bootstrap. Batches≤500, начало не чаще1/s, timeout5s, lease30s/monotonic generation, DB clock_timestamp при claim и финальном commit. Snapshots+cursor одной fenced tx; stale worker откатывает всё; сеть вне tx.

Export request after_user_id/upper_user_id optional, limit1..500. Первый source SQL определяет MAX(User.id) и LEFT JOIN Profile; source_empty явно без фиктивного ID. after требует upper, upper-only допустим; after>upper ошибка в source DB collation, after=upper пустой complete. Не менять loader.longs, версии не Number. Старый export batch не затирает новый live event; tombstone не воскресить; equal-version repair только trusted export. Созданный позади cursor UUID достигает Post через live queue; пропуски покрывает сверка. Это не единый snapshot всех пачек.

Первый READY — только fenced complete с действительным marker и подключённым Post consumer, включая пустой источник. Payment READY/marker не являются Post READY. Далее24h reconcile batch500/не чаще1s, UNIMPLEMENTED retry≥60s, transport backoff30..300s, resume cursor. Операторский дополнительный проход через nextRunAt; restart инвалидирует generation/lease/progress без удаления Post. Не scan на UI query, не публичный recovery endpoint.

Различать: NOT_READY/LOADING — неполный initial bootstrap; отсутствующая projected row — ожидаемая гонка независимых потоков/unknown; profileExists=false — подтверждённый snapshot без Profile; isDeleted=true — tombstone; storage/network failure — ошибка. Query без search не исключает unknown row, возвращает username=null; непустой search ищет только по имеющейся проекции. Это согласованный lag поиска, не ошибочная пустая initial проекция. Missing автор не блокирует всю страницу.

#### 3.1.3 Post раньше автора: готовый lookup и ограниченное восстановление

Проверено [PaymentPageProfilesQueryRepository.findProfiles](apps/main-gateway-service/src/modules/superadmin/infrastructure/payment-page-profiles.query-repository.ts): один параметризованный SELECT User LEFT JOIN Profile, включает deleted User, успешное отсутствие строки отличается от DomainException ServiceUnavailable при DB failure. Его [port](apps/main-gateway-service/src/modules/superadmin/domain/payment-page-profiles.port.ts) возвращает userId/deletedAt/profileExists/avatarUrl, не username. Cap6 позволяет lookup одного автора события без изменения общего ограничения. Минимальный reuse: export существующего PaymentPageProfiles provider из [SuperadminPaymentsModule](apps/main-gateway-service/src/modules/superadmin/superadmin-payments.module.ts) и injection в новый Gateway delivery service; не делать новый сетевой client/новый User RPC/копию SQL. Это небольшой wiring шаг, не изменение Payment бизнес-логики; avatar результата здесь не используется.

[GetUserByIdGrpcHandler](apps/main-gateway-service/src/modules/users/application/queries/get-user-by-id-grpc.query.ts) непригоден как подтверждение missing: бросает NotFound и для User, и для Profile; [User query repository](apps/main-gateway-service/src/modules/users/infrastructure/users.query-repository.ts) скрывает deleted User. Transport NOT_FOUND/timeout/пустой response не означают missing. Existing ExportPaymentUserProfiles — range export, не get-by-id: upper=id без after возвращает начало диапазона, after=upper — пустую страницу. Адресного trusted snapshot repair он не даёт. Не сканировать export до одного автора на каждом событии, не придумывать sourceVersion и не расширять RPC ради гонки.

Gateway вызывает существующий локальный lookup только для unknown projection автора published event, один раз на общую in-flight попытку/postId (при повторной попытке можно перечитать). Успешный типизированный DB результат с пустым массивом = подтверждённо missing в snapshot lookup: без search Post допускается с username=null, с непустым search не подходит. User есть (live или deleted), а projection нет — дождаться штатного sync в пределах event retry; свежий username не подставляется, версия не синтезируется. Техническая ошибка lookup остаётся ошибкой, не missing. Для profileExists=false/isDeleted=true уже имеющейся проекции дополнительный lookup не требуется. Между lookup и read возможна гонка, строгого общего snapshot не обещаем.

Post read RPC возвращает признак unknown projected row, не маскирует его как FILTERED. После подтверждения missing Gateway вправе передать внутренний boolean authorMissingConfirmed для того же postId в повторный event-view read: Post проверяет совпадение автора сохранённого Post с lookup-идентификатором события, затем сам применяет username=null и search, не Gateway after-pagination фильтрация. Внутренний authorUserId (будущий RPC author_user_id) обязателен при authorMissingConfirmed=true и проверяется против Post.ownerId; иначе boolean невозможно связать с проверенным lookup. Это техническое уточнение внутреннего кандидата, не дополнительный public input/колонка. Подтверждение действует только для unknown row этой попытки; появившаяся уже реальная projected row имеет приоритет. Это поле только нового admin event-view RPC, не существующего User RPC; обычный список его не принимает. Оно не сохраняет projected row/version и не доступно внешнему input. Таким образом используется существующий локальный lookup, а не новый большой RPC.

### 3.3 Принято: отдельный published outbox и две топологии

Добавить `PostPublishedV1` с eventId/postId/ownerId/publishedAt/schemaVersion, без описания/URL/cookies. Post + PostImage + **PostPublishedOutbox** одной createPost-транзакцией; ошибка обязательного outbox откатывает публикацию. Relay публикует сохранённый payload после commit, вне DB-транзакции; не пересобирает его из текущего Post. Delivery читает настоящий Post: уже удалённый — no-op, infrastructure failure — ошибка.

Минимальная additive Post migration: отдельная PostPublishedOutbox, id UUID PK (=eventId), postId UUID без обязательного FK, payload JSON, createdAt, availableAt, attempts default0, nullable leaseId/leaseUntil/publishedAt, безопасный lastErrorCode при необходимости. Индекс только под pending due claim (availableAt/createdAt/id, publishedAt IS NULL), парность lease-полей/неотрицательные attempts. Никаких выдуманных событий для старых Post и новой retention. Существующие **OutboxEvent/OutboxRelayCron не меняются** и не читают новую таблицу; фильтрация/двухфазное обновление delete relay не требуется.

Published relay: poll1s, SKIP LOCKED, lease30s, publish timeout5s, retry2..60s, завершение только по актуальному lease. Persistent+mandatory+correlated confirm/basic.return, messageId=eventId; eventId/payload неизменны при retry. Это broker confirmation, **не доставка конкретному Gateway/браузеру**. Confirm без basic.return означает маршрутизацию хотя бы в одну подходящую очередь: чужой wildcard binding тоже подходит. publishedAt означает подтверждённую публикацию, не ack всех Gateway. Если нет ни одного matching binding, basic.return запрещает завершить попытку; если чужой binding есть, отсутствие нужных Gateway так не обнаружить.

| Назначение               | Топология / ownership                                                                                                                     | Восстановление                                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User-profile sync в Post | common_exchange/existing payment.user-profile.changed.v1; **одна durable competing Post queue** и свои retry/DLQ, отдельные от Payment    | Commit/version guards, bootstrap/24h reconcile. Не queue на Gateway/browser                                                                                               |
| Post-published fan-out   | common_exchange/post.published.v1; **одна server-named exclusive auto-delete queue каждого Gateway**, binding до READY, локальный fan-out | Разные Gateway получают копии; не одна competing queue для всех и не queue на браузер. Потеря broker connection → завершение затронутых subscriptions → reconnect/refetch |

Ephemeral queue не replay-хранилище. Наличие всех ожидаемых bindings проверять отдельно от confirm; отключённому Gateway доставка не обещается. Enqueue в память не доказывает отправку/получение браузером. In-memory iterator — последний локальный участок, не единственный межпроцессный канал.

### 3.4 Принято: in-flight, success, отказный ack и медленный клиент

Локальные состояния postId: inFlight — одна общая promise конкурентных copies; completed — успешная обработка (bounded TTL1000 IDs/10min). Completed duplicate → ack/no-op; in-flight duplicate ждёт тот же результат, не ack заранее. Success появляется лишь после успешного read и enqueue подходящим действующим subscriptions. Временная ошибка не создаёт completed. Постоянной dedupe-таблицы/exactly-once нет.

Validation → read настоящего Post/проекции/фото → при unknown авторе один сгруппированный local lookup3.1.3 → тот же search/visibility → fresh admin session check → enqueue в отдельные buffers. Нет подходящих подписчиков/нет listeners: после успешного read ack/no-op; новые listeners восстанавливают state query, не replay. Действительно удалённый Post — окончательный no-op, не успешная доставка фиктивного Post. Если после ошибки все listeners уже закрыты, дальнейших попыток только ради них нет.

Для published event: первая попытка + **максимум3 дополнительные**, задержки **1/2/4 секунды**. Применяется к lag существующего автора без projection и transient Post/File/local lookup error. Одна in-flight обработка содержит все4 попытки; между ними timer, исходная Rabbit delivery остаётся unacked. Никаких nack(requeue=true), retry-queue, DLQ или перепубликаций ради этой гонки. RPC имеют конечный timeout5s без внутренних retries; local DB lookup использует безопасный storage mapping. Нельзя держать DB-транзакцию/row lock во время сети/таймера. Новый профиль приходит только через штатный sync/bootstrap, не через придуманный version0.

После исчерпания: completed-success **не** ставится; затронутые subscriptions завершаются безопасной UPSTREAM_UNAVAILABLE/resync; исходное сообщение **ack как отказ с восстановлением через refetch**. Это сознательно завершает broker handling, не подтверждает browser delivery. Все concurrent copies получают тот же отказный результат и ack. Отдельный bounded TTL failedRefetch (тот же cap1000/10min) различает отказ от success и позволяет уже отложенным duplicates ack/drop без нового цикла попыток; это не вечная таблица. При channel loss ack может не дойти, duplicate после crash допустим; намеренно переотправлять/переподписываться на этот event для обнуления retry-счётчика нельзя. Общий reconnect budget раздела5.2 предотвращает бесконечное создание новых подписок при сохраняющейся ошибке. После convergence проекции новый READY/refetch восстанавливает актуальный список, не replay.

Буфер **на subscription**, максимум100 событий. Overflow/неисправность одного клиента закрывает только его iterator/operation и освобождает ресурсы, остальные работают. Закрытый slow listener больше не адресат, поэтому после enqueue остальным можно завершить успешную обработку. Частичная transient server-ошибка не ставит completed: уже получившие могут увидеть повтор, frontend dedupe postId обязателен. При auth failure закрывается соответствующая subscription без retry её expired session.

RESYNC_REQUIRED best-effort: его доставка по переполненному/оборванному соединению не обязательна. Error/close/неожиданный complete тоже включают клиентское восстановление. Broker connection loss завершает все subscriptions затронутой queue/channel; незаметно продолжать нездоровую подписку нельзя. Терминально некорректный published payload отклоняется безопасным log code и ack/drop, без горячего повторения и без новой DLQ-подсистемы (это не меняет отдельный durable profile-sync retry/DLQ).

### 3.5 Принято: READY barrier и reconnect/refetch

connection_ack подтверждает соединение, не регистрацию operation. READY — только при initial projection READY, зарегистрированном **конкретном listener** и готовой Rabbit queue/binding. Listener регистрируется до READY; READY первым в operation, события этого промежутка ждут за ним в её buffer. Потеря readiness/queue между проверкой и отправкой завершает operation безопасной ошибкой.

Согласованный frontend порядок: subscribe → READY → buffer POST_PUBLISHED → первая query → merge/dedupe postId/стабильный tuple → infinite scroll. Это закрывает registration/query race, но не общий snapshot сервисов и не browser delivery acknowledgement. При NOT_READY/LOADING flow не начинается как успешный.

Reconnect/broker gap/overflow/неожиданные error/close/complete: новая subscription → новый READY → refetch головы со сбросом старой cursor chain → merge buffered events. Восстанавливается **актуальный список/окно**, не все offline публикации; старые Post доступны прокруткой. Window200 — рекомендация ограничения памяти frontend, не серверный предел глубины; scroll anchor/индикатор решает frontend без блокировки backend. Смена search также создаёт новую operation и cursor chain.

Event фильтруется по Post projection теми же правилами, что query, с отдельным подтверждением missing из3.1.3; свежий Gateway username не подставляется. Rename виден после sync и повторного чтения; eventual consistency не даёт мгновенного совпадения с Gateway. Commit бывает позже createdAt: delayed event вставляется по tuple, не обязательно в голову. Frontend dedupe дополняет локальную bounded dedupe. Realtime rename/edit/delete, browser ack и offline replay не реализуются.

## 4. Кандидат schema-first API (ещё не опубликован)

Ниже выбранный контракт реализации, ещё не опубликованный; целевые/runtime SDL сейчас неизменны (1.5.0). После реализации additive-версия по принятому порядку, ожидаемо1.6.0 при неизменной базе.

Внутренний read-кандидат через существующий PostService/channel (не временные public endpoints):

| Операция                         | Request                                                                                                                                                                        | Response / границы                                                                                                                                                                                                                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GetSuperadminPostsPage`         | first1..5/default4, optional after, optional search_username по общей нормализации                                                                                             | items≤first с postId/userId/description/сохранённой датой/ordered images и projection username; optional end_cursor, has_next_page. Нет totalCount. SQL search/visibility до pagination                                                                                                                     |
| `GetSuperadminPostPublishedView` | post_id из проверенного события, optional search_username, author_missing_confirmed=false; author_user_id обязателен при true для binding (только internal Gateway event flow) | FOUND + post; NOT_FOUND только отсутствующий/удалённый Post; FILTERED только достоверное несовпадение search; UNRESOLVED_AUTHOR при отсутствующей row без author_missing_confirmed. Внутри read-result сохранить различимость наличия projected row/profileExists/isDeleted/sourceVersion для диагностики и выбранной visibility; это не новые GraphQL поля. Отдельный public readiness endpoint не нужен. При отсутствии initial readiness обе операции UNAVAILABLE; malformed input INVALID_ARGUMENT; повреждённый upstream ответ Gateway безопасно отображает в UPSTREAM_UNAVAILABLE. Поля nullable передаются optional, не пустыми строками-датами/фиктивным username. Event fan-out группирует одинаковые нормализованные фильтры локальных подписок и читает view на distinct filter с concurrency≤4 и общим cap локальных subscriptions. Это bounded обработка; не очередь/канал на браузер и не запрос для каждой subscription с одинаковым фильтром. Не подменять PostgreSQL case-insensitive predicate похожим JS lower-case сравнением. Общий batching framework не нужен. Публикация read RPC/GraphQL — D6b, storage/application раньше.

```graphql
input SuperadminPostsInput {
  first: Int! = 4
  after: String
  searchUsername: String
}

input SuperadminPostPublishedInput {
  searchUsername: String
}

type SuperadminPostImage {
  fileId: ID!
  url: String
  order: Int!
}

type SuperadminPost {
  postId: ID!
  userId: ID!
  username: String
  description: String!
  publishedAt: DateTime!
  images: [SuperadminPostImage!]!
}

  POST_PUBLISHED

}

  kind: SuperadminPostPublishedEventKind!

  superadminPostPublished(input: SuperadminPostPublishedInput!): SuperadminPostPublishedEvent!
```

READY/RESYNC_REQUIRED имеют post=null; POST_PUBLISHED требует настоящий post. READY требует projection READY + listener registration + broker binding. RESYNC_REQUIRED — best-effort terminal control, не обязательная доставка перед close: error/неожиданный complete тоже требуют reconnect/refetch. Infra ошибки могут завершить operation безопасным UPSTREAM_UNAVAILABLE. Состояние недоступности не выдавать за items=[]. Query nullable на upstream error; auth UNAUTHENTICATED, input BAD_USER_INPUT; exact Origin rejection FORBIDDEN. WS connection errors/close codes документировать отдельно, HTTP formatter не гарантирует их обработку. `PageInfo` page-based предыдущих API не переиспользовать для cursor.

Пример будущего frontend flow: query с `input:{first:4,after:null,searchUsername:"alex"}`; следующая query с возвращённым endCursor и тем же search. Subscription с `input:{searchUsername:"alex"}`. Для block: существующий `superadminBlockUser(input:{userId:<post.userId>},reason:{code:BAD_BEHAVIOR})` через HTTP + CSRF. Другие block reasons/outcomes/legacy без изменений; admin list/detail reason read не добавляется.

## 5. Защита graphql-ws и ресурсы

Выбранный transport path: `/api/v1/graphql` на том же HTTP server, subprotocol `graphql-transport-ws`; cookie path уже подходит. Фактический `wss://<Gateway host>/api/v1/graphql` неизвестен. Сохранить `/socket.io` и проверить их совместные upgrade listeners: установленный Nest делает prefix-path match, поэтому нужен точный path gate, а не доверие startsWith.

- Upgrade: exact Origin из существующего parseSuperadminOrigins, отсутствие Origin отклонять для browser API; ограничить path/subprotocol и handshake size/time. Проверка нужна до допуска operation; CORS не является WS-защитой. Не принимать credentials из URL, Authorization user JWT или connectionParams как замену admin cookie.
- `onConnect` разбирает cookie upgrade request и использует существующий AdminPrincipalVerifier; `onSubscribe` повторяет проверку и валидирует schema/input/budget/operation. На WS разрешить только subscription этого экрана; query/mutation остаются HTTP. Не переносить mutation-CSRF протокол в subscription.
- Новый discriminated HTTP/WS context: WS хранит upgrade request, principal, connection lifecycle; res отсутствует. Адаптировать root/nested guard и exception filter для обоих видов без ложного HTTP Response. Не вызывать cookie bootstrap из WS. Проверить aliases/fragments и nested fields.
- Перед каждым protected event — fresh session check, storage failure fail-closed; общий sweep каждые30s закрывает revoked/expired idle connections. Выделить non-touch чтение той же AdminSession, чтобы heartbeat/доставка сами не продлевали idle30min. Явные HTTP действия сохраняют прежний bounded touch; initial subscribe может использовать существующий verifier. Не создавать вторую session system. Idle socket может закрыться раньше8h согласно существующему idle expiry.
- Локальные стартовые лимиты: 1 active operation/connection, 5 connections/admin session/экземпляр, общий cap100/экземпляр, init timeout5s, maxPayload64KiB, pending buffer100 событий/subscription. Это локальные лимиты, не глобальные гарантии при нескольких pods; ingress/IP rate limits проверить в окружении. При overflow закрывается только медленная subscription, остальные работают; resync notification best-effort. Это выбранные стартовые параметры, не измеренный SLA.
- Использовать существующие depth8/complexity200 и правила aliases/fragments на `onSubscribe`, точечно разрешив новый Subscription root. Учитывать first1..5/default4 и до10 images/item по расчёту5.3; запрос сверх200 отклонять, не повышать глобальный budget. HTTP body/batching/introspection policy не ослаблять.
- Disconnect/complete/error: iterator.return, удаление listeners/timers/buffers/session mapping. Shutdown: прекратить upgrade, dispose subscription server, cancel Rabbit consumer/закрыть channel и ресурсы, завершить pending operations. Логи: только безопасный code/event/progress, без payload, описания, username, cookies/tokens.

### 5.1 Heartbeat и ownership WebSocket server

Проверен установленный graphql-ws6.2.1 dist/use/ws.cjs (useServer): уже есть **WebSocket protocol** ping/pong, default12s; один keepAlive параметр задаёт и interval, и pong deadline. Nest13.4.5 GqlSubscriptionService вызывает useServer без третьего аргумента, его options не позволяют раздельно выставить25s/10s. Socket.IO /socket.io heartbeat к этому серверу не относится.

Минимальное конкретное решение: небольшой Gateway lifecycle provider SuperadminSubscriptionServer на существующем HTTP server, WebSocketServer(noServer,maxPayload64KiB) и useServer(schema из GraphQLSchemaHost, hooks/context, keepAlive=0). Не включать одновременно Nest built-in subscriptions: иначе будет второй upgrade listener/heartbeat. HTTP Apollo/schema-first resolvers остаются прежними; защищённые hooks используют ту же фактическую schema/guards. Provider сам обрабатывает только exact /api/v1/graphql + graphql-transport-ws, остальные upgrade не захватывает (Socket.IO продолжает работать). Это scoped adapter одного endpoint, не новый framework/server/service.

Установленный useServer heartbeat отключён третьим аргументом0; один собственный protocol ping каждые25s, один pending nonce и deadline10s. Только соответствующий protocol pong снимает deadline; иначе terminate, клиент обычно видит abnormal close1006. Браузер автоматически отвечает protocol pong, JS не должен отправлять protocol ping. graphql-ws JSON ping/pong — другие сообщения: они не подтверждают protocol nonce. Init wait5s; heartbeat никогда не вызывает touch/session extension. Session sweep30s/fresh check перед delivery сохраняются независимо.

На close/shutdown снимать ping interval/pong timeout/listener, закрывать sockets/iterators, dispose useServer и WSS, снимать свой HTTP upgrade listener. Не выводить raw library errors/headers/payload в лог: hooks/transport ошибки оборачивать безопасным кодом. Proxy idle timeout **минимум60s**, больше25s с запасом; фактическую конфигурацию проверить в окружении.

Frontend слушает close/error и запускает5.2; browser protocol frames ему не видны. Дополнительный периодический JSON heartbeat/watchdog не вводится: server protocol heartbeat ограничивает мёртвые server connections. При network blackhole browser может не узнать о закрытии мгновенно; не обещать фиксированное время browser detection. На восстановлении сети/возврате приложения можно проверить существующий session flow и запустить тот же bounded reconnect supervisor; не параллельный вечный timer-loop.

### 5.2 Единая bounded reconnect политика frontend

Один supervisor для connection loss **и terminal operation errors**, включая initial NOT_READY: задержки1/2/4/8/16/30s, далее30s; jitter±20%, максимум10 последовательных неудачных попыток, включая первую немедленную (не более9 автоматических повторов); затем видимая безопасная ошибка и ручной Retry. Только ручной Retry или новый успешный login начинает явно новую серию. На connection_ack/open счётчик **не** сбрасывается: reset после READY + успешной первой query и30s стабильного соединения. Быстрый READY→error/resync остаётся в той же серии. Ожидание READY ограничить15s после ack одним startup timer (не heartbeat), дальше тот же transport/upstream backoff.

Для Apollo GraphQLWsLink: graphql-ws client retryAttempts=0, JSON keepAlive=0; единственным владельцем retries остаётся supervisor, пересоздающий client/operation по расписанию и dispose старого. Так operation Error и transport Close не запускают два цикла, и внутренний сброс graphql-ws retry counter на ack не обходит предел. При нормальном unsubscribe/navigation/logout dispose отменяет timers и retries. Не применять общий Apollo RetryLink к WS/этим terminal errors. Unknown network break сначала transport failure, не доказательство expired session/Origin; после10 неудач не продолжать тайно.

Коды сверены с установленным graphql-ws6.2.1 (dist/common-DqFHi7oM.cjs, client.cjs, server-DN5-9C2B.cjs). Они **проектируемый mapping**, ещё не работающий API. Встроенный onConnect return false закрывает4403, поэтому для отсутствующей/expired session явно закрывать extra.socket с4401 и безопасной причиной, не смешивать с Origin. Не бросать raw Error из hook: это даёт4500/внутренний error path. Operation errors возвращать безопасными GraphQLError с существующими extensions.code через scoped formatter.
